Claude Code skill examples: 5 SKILL.md files you can copy (validated)

A skill is a folder with a SKILL.md file: a short description that tells Claude when to use it, and the steps to follow. Five copy-paste skills below, each checked with claude plugin validate.

How a skill works

  • Where: .claude/skills/<name>/SKILL.md in a project (share it with the repo), or ~/.claude/skills/<name>/SKILL.md for all your projects. Plugins can ship skills too.
  • Frontmatter: name (lowercase, hyphens) and description are the two that matter. allowed-tools lets the skill use the listed tools without asking. Newer versions support more fields; check the skills docs for your version.
  • When it runs: Claude sees every skill's description and loads the full file only when a task matches. You can also call one directly with /name.
  • The description decides everything. Say what it does and when to use it ("Use when the user asks for…"). A vague description means the skill never fires.

1. Commit message from the staged diff

Reads only the staged diff and the last 10 commits, matches the repo's style, and commits only when asked. allowed-tools lets it run those git commands without a permission prompt.

.claude/skills/commit-message/SKILL.md

---
name: commit-message
description: Write a commit message from the staged diff. Use when the user asks for a commit message or asks Claude to commit staged changes.
allowed-tools: Bash(git diff:*), Bash(git log:*), Bash(git status:*)
---

# Commit message

1. Run `git diff --cached`. If nothing is staged, say so and stop. Do not stage files yourself.
2. Run `git log --oneline -10` and match the repo's style (Conventional Commits, ticket prefixes, tense).
3. Write a subject of 72 characters or less that says what changed and why, in the imperative.
4. Add a body only when the why is not obvious from the subject. Wrap at 72 characters.
5. Show the message. Commit only if the user asked you to commit.

2. Fix a failing test (the cause, not the test)

The most useful rule here is step 5: Claude sometimes makes a test pass by loosening it. Saying it plainly in a skill stops most of that.

.claude/skills/fix-failing-test/SKILL.md

---
name: fix-failing-test
description: Find out why a test fails and fix the cause, not the test. Use when a test, CI job or test command fails.
---

# Fix a failing test

1. Run the single failing test and read the full error, not just the last line.
2. Say in one sentence what the test expects and what happened instead.
3. Find the cause in the code under test. Read the recent diff (`git diff`, `git log -p -3 -- <file>`) first.
4. Fix the code. Change the test only if the test itself is wrong, and say why.
5. Never skip, delete or loosen a test to make it pass.
6. Run the failing test again, then the whole suite, and report both results.

3. Changelog entry

Keeps the file's own format and writes for users. It never edits released sections.

.claude/skills/changelog-entry/SKILL.md

---
name: changelog-entry
description: Add an entry to CHANGELOG.md for the current change. Use when the user asks to update the changelog or prepare a release.
---

# Changelog entry

1. Open CHANGELOG.md. If it doesn't exist, ask before creating one.
2. Follow the file's format. If it uses Keep a Changelog, add the entry under `## [Unreleased]`
   in the right group: Added, Changed, Deprecated, Removed, Fixed, Security.
3. Write for users, not reviewers: what they will notice, in one line each. Link the PR or issue if the file does.
4. Don't change existing released sections.
5. Show the diff of CHANGELOG.md when done.

4. Codebase tour

Read-only by design: allowed-tools lists only reading tools, and the last line says not to change files. Good first skill for onboarding.

.claude/skills/codebase-tour/SKILL.md

---
name: codebase-tour
description: Give a short guided tour of an unfamiliar repository. Use when the user is new to a codebase or asks how it is laid out or where to start.
allowed-tools: Read, Grep, Glob, Bash(git log:*), Bash(ls:*)
---

# Codebase tour

1. Read README, CLAUDE.md and the build file (package.json, pyproject.toml, go.mod, Cargo.toml, Makefile).
2. List the top-level folders and say in one line what each one holds.
3. Find the entry points (main, server start, CLI) and trace one real request or command through the code.
4. Show how to run it, test it and lint it, with the exact commands from the repo.
5. Name the 5 files a new contributor should read first, and why.
Keep it under one screen. Don't change any files.

5. Secret check before commit or push

A skill is advice Claude follows; it can't stop a commit. Pair it with a PreToolUse hook if you need a hard block (see block dangerous commands).

.claude/skills/secret-check/SKILL.md

---
name: secret-check
description: Check a diff for secrets before it is committed or pushed. Use before a commit or push, or when the user asks whether a change leaks credentials.
allowed-tools: Bash(git diff:*), Grep
---

# Secret check

1. Run `git diff --cached` (or `git diff <base>...HEAD` before a push).
2. Look for API keys, tokens, private keys, passwords, connection strings and .env contents in added lines.
   Common shapes: `sk-`, `ghp_`, `AKIA`, `-----BEGIN`, `password=`, `postgres://user:pass@`.
3. Check that new files like `.env`, `*.pem` and `credentials.json` are ignored by `.gitignore`.
4. Report each finding with file and line, and mask the value (show only the first 4 characters).
5. If you find one, stop: don't commit or push. Tell the user to remove it and rotate the key.

Check them

Put the folders in a plugin layout and run the validator. It checks every SKILL.md's frontmatter:

$ claude plugin validate .
√ Validation passed with warnings

(The only warning was a missing plugin icon.) Then ask Claude "write a commit message" in a repo with staged changes and check that it says it's using the commit-message skill.

Skill not firing?

  • Make the description concrete: name the trigger words a user would type.
  • Check the folder name and the file name: it must be SKILL.md inside its own folder.
  • Start a new session after adding a skill, then run /name once to confirm it loads.
