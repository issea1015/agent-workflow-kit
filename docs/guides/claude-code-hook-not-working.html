Claude Code hook not working? A 7-step debugging checklist

A hook that silently does nothing is worse than no hook: you think you're protected and you aren't. Go through these seven checks in order. Most broken hooks fail on the first three.

1. Is the settings file valid JSON?

One trailing comma and the whole file is ignored. Check it before anything else:

python3 -m json.tool .claude/settings.json > /dev/null && echo valid

A broken file prints the position of the error, for example Expecting value: line 1 column 27 (char 26).

2. Is it in a file Claude Code reads?

  • ~/.claude/settings.json: user-wide
  • .claude/settings.json: this project, usually committed
  • .claude/settings.local.json: this project, just for you
  • hooks/hooks.json: inside a plugin

A hook written into settings.json at the project root, is never loaded.

3. Is the event name spelled exactly right?

Event names are case-sensitive keys under "hooks": PreToolUse, PostToolUse, UserPromptSubmit, SessionStart, Stop, and so on. preToolUse or PreToolUses is just an unknown key.

4. Does the matcher match the tool name?

The matcher is matched against the tool name, and tool names are capitalized: Bash, Edit, Write, Read. A matcher of bash never fires. To match several tools use Edit|Write; to match all of them use *.

5. Does the script exist where the command looks for it?

Hook commands don't always run from the folder you expect. A relative path like python3 .claude/hooks/guard.py breaks as soon as the working directory differs. Anchor it to the project instead:

"command": "python3 \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/guard.py"

If you call the script directly (./guard.sh), it also needs to be executable: chmod +x .claude/hooks/guard.sh.

6. Does the script exit with the right code?

A PreToolUse hook blocks a call only when it exits with code 2; its stderr is then shown to Claude as the reason. Exit 0 allows the call. Any other non-zero code is reported as a hook error but does not block. Test the script by hand with the JSON Claude Code sends on stdin:

echo '{"tool_name":"Bash","tool_input":{"command":"rm -rf ~"}}' \
  | python3 .claude/hooks/guard.py; echo "exit=$?"

With the free guard-dangerous-bash hook this prints:

Blocked by guard-dangerous-bash: recursive delete of the root or home directory. If this is really intended, run it yourself outside Claude Code.
exit=2

A common bug: a Python script that raises an exception exits with 1, so the dangerous command goes through.

7. Did Claude Code pick up the change?

Claude Code reads hooks when a session starts, so edits made mid-session may not apply yet. Open the /hooks menu to see what's actually loaded, or start Claude Code with claude --debug to see each hook run and its exit code.

Check steps 1–6 automatically (free)

hook_doctor.py is a free, read-only script that runs the checks above for you: JSON, event names, matcher case, missing or non-executable scripts, and relative paths. With no arguments it checks every settings file Claude Code reads.

$ python3 hook_doctor.py .claude/settings.json
ERROR .claude/settings.json hooks.PreToolUse[0]: matcher 'bash' never matches: tool names are case-sensitive, use 'Bash'
WARN  .claude/settings.json hooks.PreToolUse[0]: .claude/hooks/guard.py is relative to the working directory; use "$CLAUDE_PROJECT_DIR"/.claude/hooks/guard.py
ERROR .claude/settings.json hooks.PreToolUse[0]: script not found: .claude/hooks/guard.py
checked 1 file(s): 2 error(s), 1 warning(s)

Audit what your hooks do

The kit's audit.py --settings reads every hook in a settings file and follows each command into its script. It's built for security (download-and-run, obfuscation, secret access), and it also flags hooks whose script doesn't exist. For a settings file with a lowercase matcher and a missing script:

$ python3 tools/audit.py --settings .claude/settings.json
MEDIUM missing-script   .claude/settings.json hooks.PreToolUse[0] matcher='bash': script not found: .claude/hooks/guard.py
audited 1 hook command(s) in 1 file(s): PASS (0 high, 1 other)

The matcher is printed so you can spot 'bash' vs 'Bash' at a glance.
